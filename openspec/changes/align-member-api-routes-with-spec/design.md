## Context

현재 `src/app/api` 아래 회원/검색/리뷰 라우트는 대부분 백엔드 API를 프록시하는 형태로 구현되어 있습니다. 이번 change의 목표는 주어진 명세 기준으로 라우트 동작을 고정하고, 구현 단계에서 정합성 점검 및 필요한 수정을 안전하게 진행할 수 있는 기준(spec/tasks)을 만드는 것입니다.

핵심 제약은 다음과 같습니다.
- 인증은 `accessToken` 쿠키 기반으로 처리됩니다.
- 백엔드 기본 URL은 `EXTERNAL_API_BASE_URL` 환경변수에 의존합니다.
- 프론트는 BFF 라우트(`/api/...`)를 통해 백엔드 `/v1/...` 엔드포인트를 호출합니다.

## Goals / Non-Goals

**Goals:**
- 명세에 포함된 대상 엔드포인트의 method/path/body 전달 규칙을 명확히 정의한다.
- 인증 토큰 누락 시 처리와 백엔드 응답(status/body) 전달 방식의 일관성을 정의한다.
- 구현 단계에서 검증 가능한 작업 체크리스트를 만든다.

**Non-Goals:**
- 백엔드 도메인 로직 변경
- 프론트 UI/화면 변경
- 명세에 없는 신규 엔드포인트 추가

## Decisions

1. 엔드포인트별 프록시 구조를 유지한다.
- 이유: 현재 코드 구조와 호출 경로를 유지하면서 영향 범위를 최소화할 수 있습니다.
- 대안: 단일 범용 프록시 라우트로 통합
- 미채택 이유: 기존 라우트 계약 변경 폭이 커지고 디버깅 경로가 불명확해질 수 있습니다.

2. 인증 토큰 사전 검사를 모든 대상 라우트에 동일하게 적용한다.
- 이유: 인증 실패 케이스를 백엔드 호출 전에 빠르게 차단하고, 클라이언트 동작을 예측 가능하게 만듭니다.
- 대안: 백엔드에 위임하고 프록시에서는 무조건 전달
- 미채택 이유: 프록시 계층의 책임이 불명확해지고 불필요한 백엔드 트래픽이 발생합니다.

3. 백엔드 응답은 가능한 한 status/body를 그대로 전달한다.
- 이유: 명세의 성공/실패 상태 코드를 프론트에서 정확히 처리할 수 있습니다.
- 대안: 프록시 레이어에서 상태 코드/메시지를 재매핑
- 미채택 이유: 명세 추적이 어려워지고 회귀 포인트가 증가합니다.

4. 구현 시 공통 처리(토큰 추출, ky 요청 옵션, 공통 에러 응답)는 중복 제거를 검토한다.
- 이유: 다수 route 파일에서 동일 패턴이 반복되어 유지보수성이 낮습니다.
- 대안: 현재 파일별 중복 유지
- 미채택 이유: 향후 API 추가 시 실수 가능성이 커집니다.

## Risks / Trade-offs

- [Risk] 명세 원문 일부가 잘린 상태라 세부 필드 정의가 누락될 수 있음
  - Mitigation: 구현 전 request/response schema 필드 재확인, 최소한 method/path/status 기준으로 우선 정렬
- [Risk] 공통화 리팩터링 시 기존 동작이 변할 수 있음
  - Mitigation: 엔드포인트별 회귀 체크리스트와 수동 검증 시나리오를 tasks에 포함
- [Trade-off] status/body pass-through를 우선하면 프론트 친화적 에러 메시지 표준화는 늦춰짐
  - Mitigation: 본 change에서는 정합성 우선, 에러 포맷 표준화는 후속 change로 분리
